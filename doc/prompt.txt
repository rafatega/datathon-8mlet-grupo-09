# Datathon MLET — Planejamento e Desenvolvimento End-to-End

Você é o agente responsável por conduzir o desenvolvimento completo de um projeto de Datathon de Machine Learning Engineering.

O projeto deve ser desenvolvido de forma **end-to-end**, com foco em simplicidade, funcionamento real, reprodutibilidade, qualidade técnica e capacidade de demonstrar/defender as decisões tomadas.

## 1. Fonte principal de requisitos

O arquivo PDF do desafio fornecido junto a este prompt é a fonte principal dos requisitos obrigatórios.

Antes de iniciar qualquer implementação:

1. Leia integralmente o PDF.
2. Extraia todos os requisitos, restrições, entregáveis e critérios de avaliação.
3. Transforme esses requisitos em um checklist técnico.
4. Identifique o que é:
   - obrigatório;
   - recomendado;
   - opcional;
   - não especificado no documento.
5. Não invente requisitos do desafio.
6. Não descarte nenhum requisito explícito do PDF.

O objetivo principal é entregar exatamente o que a banca espera, sem adicionar complexidade desnecessária.

A prioridade deve ser:

**Requisito do desafio > funcionamento correto > arquitetura coerente > conceitos aprendidos no módulo > complexidade adicional.**

# 3. Use uma abordagem Multi-Agent / Superpowers

Antes de implementar, utilize o sistema de agentes disponível no ambiente (Superpowers ou equivalente) para dividir o trabalho em etapas especializadas.

Não permita que um único agente simplesmente gere todo o projeto sem validação.

Estruture o trabalho, no mínimo, com os seguintes papéis:

### Agent 1 — Requirements Analyst

Responsável por:

- analisar o PDF;
- extrair requisitos;
- identificar entregáveis;
- identificar critérios de avaliação;
- montar checklist;
- identificar ambiguidades;
- separar requisitos obrigatórios de opcionais.

### Agent 2 — Data Scientist / ML Specialist

Responsável por:

- analisar datasets candidatos;
- avaliar adequação do dataset ao problema;
- definir target;
- definir features;
- identificar leakage;
- propor baseline;
- propor algoritmo adaptativo;
- definir estratégia de recompensa;
- definir metodologia de avaliação;
- avaliar se Thompson Sampling, Epsilon-Greedy, UCB ou abordagem contextual é adequada.

### Agent 3 — MLE / Architecture

Responsável por:

- propor arquitetura end-to-end;
- avaliar Data Storage;
- avaliar Feature Store;
- definir pipeline de dados;
- definir estrutura do projeto;
- definir serving;
- avaliar Docker;
- avaliar deploy;
- avaliar Vercel;
- definir estratégia de MLflow;
- avaliar quais componentes realmente são necessários.

### Agent 4 — MLOps / Production

Responsável por:

- reprodutibilidade;
- versionamento;
- MLflow;
- Docker;
- testes;
- CI/CD, se fizer sentido;
- deploy;
- observabilidade;
- configuração de ambiente;
- gerenciamento de dependências;
- segurança básica.

### Agent 5 — Reviewer / Red Team

Responsável por revisar criticamente o plano antes da implementação.

Deve procurar:

- leakage;
- metodologia inválida;
- reward mal definido;
- baseline inadequado;
- comparação injusta;
- data leakage temporal;
- overfitting;
- métricas inadequadas;
- complexidade desnecessária;
- arquitetura incoerente;
- requisitos do PDF não atendidos;
- funcionalidades adicionadas apenas para "encher requisito";
- problemas no deploy;
- problemas de Docker;
- problemas de reproducibilidade;
- problemas nos testes;
- problemas na apresentação final.

### Agent 6 — Final Auditor

Depois da implementação, deve revisar o projeto inteiro contra o checklist original e informar:

- requisitos atendidos;
- requisitos parcialmente atendidos;
- requisitos não atendidos;
- riscos;
- problemas técnicos;
- melhorias necessárias antes da entrega.

# 5. Dataset

O desafio exige uma base Kaggle compatível com:

- marketing;
- ofertas;
- propensão;
- campanhas;
- recomendação;
- conversão.

As bases sugeridas no documento devem ser consideradas.

Avalie pelo menos as alternativas relevantes antes de escolher.

Para cada dataset candidato, avalie:

- tamanho;
- features;
- target;
- existência de múltiplos braços;
- possibilidade de simular/representar ações diferentes;
- qualidade dos dados;
- missing values;
- leakage;
- temporalidade;
- possibilidade de construir uma política adaptativa;
- facilidade de demonstrar o projeto;
- licença/fonte;
- limitações.

Não escolha um dataset apenas porque é mais fácil.

Escolha o dataset que permita construir o experimento mais coerente com o desafio.

# 6. Definição do problema de Bandit

Essa é uma das partes mais importantes.

Defina explicitamente:

### Contexto

Quais características do cliente entram na decisão?

### Arms

Quais são as ofertas/mensagens/ações disponíveis?

### Reward

Qual evento representa sucesso?

Exemplo:

```text
reward = 1 → conversão
reward = 0 → não conversão
```

Mas não assuma esse formato sem analisar o dataset.

### Policy

Avaliar:

- Thompson Sampling;
- Epsilon-Greedy;
- UCB;
- contextual bandit, se fizer sentido.

O documento permite essas alternativas, desde que a escolha seja justificada.

Escolha a abordagem que melhor equilibre:

- aderência ao desafio;
- qualidade metodológica;
- simplicidade;
- possibilidade de explicação;
- capacidade de demonstração.

---

# 7. Baseline

O baseline deve ser definido antes do modelo adaptativo.

Possibilidades:

- melhor braço histórico;
- regra fixa;
- mesma oferta para todos;
- política simples baseada em histórico;
- outro baseline justificável.

Documente:

```text
Baseline
↓
Hipótese
↓
Métrica
↓
Resultado
```

Não manipule o experimento para garantir artificialmente que o algoritmo adaptativo vença.

Se o algoritmo adaptativo não superar o baseline, investigue o motivo.

Possíveis causas:

- reward inadequado;
- exploração excessiva;
- dataset inadequado;
- algoritmo inadequado;
- baseline forte;
- simulação inadequada;
- falta de contexto;
- bug.

O resultado deve ser metodologicamente defensável.

---

# 8. Avaliação

Defina previamente as métricas.

Não use somente accuracy sem avaliar se ela representa o problema.

Considere, conforme aplicável:

- conversion rate;
- cumulative reward;
- regret;
- reward médio;
- exploração vs. exploração;
- performance por segmento;
- performance por braço;
- estabilidade;
- comparação com baseline.

Explique por que cada métrica foi escolhida.

A avaliação deve permitir responder:

> "O sistema adaptativo realmente aprende uma política melhor do que a política baseline?"

# 9. Data Leakage

Faça uma revisão específica de leakage.

O PDF menciona explicitamente a necessidade de descartar colunas de vazamento temporal, como `duration` no Bank Marketing.

Portanto:

1. Identifique possíveis colunas de leakage.
2. Justifique a remoção.
3. Documente isso no projeto.
4. Garanta que nenhuma informação disponível apenas após a decisão seja utilizada como feature.

Faça uma revisão independente especificamente para isso.

# 11. Feature Store

Avalie criticamente se uma Feature Store realmente faz sentido.

Perguntas que devem ser respondidas:

1. Existe reutilização relevante das features?
2. Existe necessidade de consistência entre treinamento e serving?
3. Existe pipeline de atualização?
4. Existe necessidade de versionamento das features?
5. O projeto se beneficia de separar feature computation de model serving?
6. A complexidade adicional é justificável para o tamanho do projeto?

Se a resposta for não:

> NÃO implementar uma Feature Store artificial.

Nesse caso, documentar a decisão e explicar como o conceito poderia ser utilizado em uma arquitetura de produção maior.

Se fizer sentido, implementar uma versão proporcional ao projeto, sem criar infraestrutura desnecessária.

# 13. Docker

O projeto deve ser avaliado para execução containerizada.

Caso faça sentido — e salvo incompatibilidade com a plataforma de deploy escolhida — criar:

```text
Dockerfile
.dockerignore
requirements.txt ou pyproject.toml
```

O container deve permitir reproduzir o ambiente da aplicação.

Validar:

1. build da imagem;
2. criação do container;
3. execução;
4. acesso à aplicação/API;
5. funcionamento do modelo;
6. configuração via environment variables;
7. ausência de dependências locais ocultas.

Documentar os comandos necessários.

Exemplo conceitual:

```bash
docker build ...
docker run ...
```

Não assumir que "ter Dockerfile" significa que Docker está funcionando.

O container precisa ser efetivamente testado.

# 14. Deploy

O PDF exige uma arquitetura-alvo em cloud e uma interface/serviço demonstrável.

O ambiente planejado para deploy será **Vercel**, mas NÃO assuma que Vercel é automaticamente a melhor ou tecnicamente compatível solução para todos os componentes.

Antes da implementação:

- valide a compatibilidade do serving com Vercel;
- valide limitações de runtime;
- valide suporte ao formato do modelo;
- valide limitações de tempo/memória;
- valide como o modelo será carregado;
- valide como o endpoint será exposto;
- valide se o Docker será utilizado diretamente ou apenas no processo de desenvolvimento/build;
- valide se existe algum componente que deve ser hospedado separadamente.

Se Vercel não for adequado para determinado componente, não force a arquitetura.

Proponha a solução mínima compatível.

# 20. Riscos que devem ser monitorados

Durante todo o desenvolvimento, mantenha uma seção de riscos.

No mínimo avaliar:

### Risco 1 — Data Leakage

Principalmente leakage temporal.

### Risco 2 — Reward mal definido

O reward precisa representar corretamente o objetivo do problema.

### Risco 3 — Bandit artificial

Evitar criar uma simulação onde o algoritmo necessariamente ganha.

### Risco 4 — Baseline inadequado

O baseline precisa ser uma comparação razoável.

### Risco 5 — Overengineering

Não criar infraestrutura apenas para demonstrar tecnologia.

### Risco 6 — Dataset inadequado

O dataset precisa permitir representar o problema de decisão adaptativa.

### Risco 7 — Deploy incompatível

Validar Vercel e runtime antes de construir a arquitetura final.

### Risco 8 — Reprodutibilidade

Outra pessoa deve conseguir executar o projeto.

### Risco 9 — Model serving inconsistente

Garantir que preprocessing utilizado em treinamento seja o mesmo utilizado em inferência.

### Risco 10 — Resultado não reproduzível

Fixar seeds quando apropriado e registrar parâmetros/versões.

### Risco 11 — Complexidade excessiva

Sempre perguntar:

> "Isso melhora a solução ou apenas aumenta a quantidade de tecnologia?"
